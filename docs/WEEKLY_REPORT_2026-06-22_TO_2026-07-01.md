## 1. Competitor Visibility Scoring Was Added

The largest change was a new competitor score read model. This gives the gateway a way to score competitor domains against the primary site, store those scores over time, and expose scorecards, trends, and gap opportunities to the dashboard.

### What was added

- A new migration, `migrations/0005_competitor_score_snapshots.sql`, extends the `competitors` table and creates `competitor_score_snapshots`.
- The migration adds competitor metadata fields such as `status`, `color_key`, `source_metadata`, `last_assessed_at`, `last_error`, and `updated_at`.
- It creates snapshot storage for each competitor by site, date window, range, model version, scores, metrics, source scores, issue distribution, evidence, freshness, and missing-data metadata.
- It adds unique and lookup indexes so snapshots can be safely upserted and queried by site/range or competitor/day.
- `scripts/migrate.js` now includes the new migration in the migration list.
- `src/data/schema.js` now treats `competitors` and `competitor_score_snapshots` as required tables.

### Why it matters

Before this work, the gateway had site-level scoring but did not have a dedicated historical read model for competitor scorecards. The dashboard could not reliably ask, "How do we compare against these competitors over the selected range?" without recomputing or stitching together raw inputs.

The new snapshot table gives the application a stable backend contract for competitor scorecards and trend lines.

## 2. Competitor Score Model Was Implemented

A new scoring module was added in `src/lib/competitor-score-scoring.js`.

### What it computes

The model produces a versioned score payload under `gpto.competitor_visibility.v1`, including:

- Overall AI visibility
- ChatGPT-specific score
- Google AI Overviews score
- AI audience estimate
- Website audience value when available
- Mentions
- Citations
- Cited pages
- Share of voice
- Authority proxy
- Internal readiness
- Public footprint
- Content readiness
- Technical readiness
- Schema readiness

### Data completeness handling

The scorer explicitly distinguishes between complete and partial data states:

- `complete` when external AI visibility, crawl, and audience inputs are available.
- `partial_external_missing` when external AI visibility data is missing.
- `partial_crawl_missing` when public crawl data is missing.
- `partial_traffic_missing` when website audience data is missing.

When external competitor data is unavailable, the scorer can fall back to public estimates based on crawl and server-readiness signals. This keeps the dashboard from going blank while still marking that the score is estimated.

### Domain normalization

The scorer normalizes competitor domains by stripping protocol, `www.`, paths, and ports. This avoids treating `https://www.example.com/path` and `example.com` as separate competitors.

## 3. Competitor Materialization Was Added

A new service, `src/services/competitor-score-materialize.js`, materializes competitor snapshots.

### What the materializer does

For each active site and competitor, it can generate snapshots for `7d`, `30d`, and `90d` ranges. It gathers:

- LLM mention rollups for competitor comparison data.
- Prompt observations where the competitor appears in cited or retrieved domains.
- Public server checks for the competitor domain.
- Homepage crawl facts such as title, description, word count, headings, links, and schema types.
- Robots.txt status and AI bot blocking signals.
- Sitemap status, URL count, homepage inclusion, and sample URLs.
- `llms.txt` availability.

It then computes a score snapshot and stores it in `competitor_score_snapshots`.

### Operational behavior

- Supports `dryRun`.
- Supports `skipCrawl`.
- Supports specific site, competitor, and range targeting.
- Updates `competitors.last_assessed_at` when a competitor is successfully assessed.
- Marks a competitor as `failed` and stores `last_error` if materialization fails.

### Cron integration

`src/services/dashboard.js` now calls `materializeCompetitorScores()` during `runDashboardCronRefresh()`, after telemetry, suite materialization, and site score materialization. The cron response now includes `competitorScoreMaterialize` so operators can see whether competitor scoring ran.

## 5. Telemetry Page Reporting Was Cleaned Up

The second major change was a telemetry cleanup focused on preventing noisy or misleading pages from appearing in dashboard top-page reports.

A new shared helper module was added in `src/lib/telemetry-pages.js`.

### What it filters

The helper excludes:

- WordPress admin URLs, including `/wp-admin` and `/wp-login.php`
- WordPress editor/customizer/preview query parameters
- Non-HTTP URLs
- Pages marked as not found
- Pages whose title indicates a 404 or not-found page

Examples of filtered editor parameters include:

- `vc_editable`
- `vc_post_id`
- `_vcnonce`
- `elementor-preview`
- `wp_customize`
- `customize_changeset_uuid`
- `preview=true`

### What it normalizes

The helper normalizes public page URLs by:

- Lowercasing the hostname
- Removing query strings and fragments
- Keeping the canonical protocol, host, and path
- Aggregating query-string variants into one top-page entry

For example, traffic to `https://example.com/?ex_cid=campaign#top` now aggregates under `https://example.com/`.

## 6. Telemetry Daily Rollups Were Reworked

`src/services/telemetry-daily-rollup.js` was changed from SQL-only aggregation to application-level processing of telemetry event rows.

### What changed

The rollup now:

- Reads event rows for the site/day window.
- Extracts page details from `page`, `context`, and `metrics`.
- Ignores WordPress admin/editor traffic before counting page views.
- Counts valid page views, searches, and interactions.
- Tracks visits from sessions, with fallbacks to page views, interactions, or searches.
- Builds top pages through the new shared telemetry page aggregator.
- Builds top intents from valid counted events.
- Writes `top_pages` and `top_intents` as JSON.
- Updates `sites.last_telemetry_at` based on the latest event timestamp.

### Why it matters

Dashboard top pages should represent public customer-facing pages, not internal editing sessions or broken pages. This change makes the rollup stricter and keeps the downstream dashboard, gold report, and PDF outputs cleaner.

## 7. Dashboard, Gold, and PDF Outputs Now Use the Same Top-Page Rules

The new telemetry page helper is now reused in multiple output paths:

- `src/builders/telemetry.js`
- `src/builders/gold.js`
- `src/pdf/render.js`

This avoids a common class of bugs where the dashboard, customer insights, and PDF export all present slightly different versions of "top pages."

### Dashboard telemetry builder

`buildTelemetry()` now:

- Loads known not-found URL keys from telemetry events.
- Aggregates all daily rollup top pages through the shared cleaner.
- Limits the final top-page list to 10 entries.

### Gold/customer insights builder

Customer insights now use cleaned and aggregated top pages before displaying page-level traffic highlights.

### PDF export

The telemetry page in the PDF now uses the same public-page aggregation logic, so reports should not surface WordPress editor URLs or 404 pages in the top-page table.
