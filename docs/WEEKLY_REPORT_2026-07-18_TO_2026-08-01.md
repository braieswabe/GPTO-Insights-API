## 1. DataForSEO Automation Was Added

The largest change was a new durable automation layer for DataForSEO LLM Mentions pulls. Instead of relying on ad-hoc refreshes, the gateway can now queue work, process it asynchronously, retry failures, and report status.

### What was added

- A new migration, `migrations/0006_dataforseo_automation.sql`, creates:
  - `dataforseo_automation_batches` for scheduled or manual runs
  - `dataforseo_automation_jobs` for per-site, per-endpoint work items
- Batch rows track trigger type, optional Manila schedule key, source, status, job counts, and timestamps.
- Job rows track endpoint, status, attempts, locks, linked snapshot ID, process summary, cost, and errors.
- Unique indexes prevent duplicate scheduled batches for the same day/source and duplicate jobs within a batch.
- Claim and batch indexes support worker polling and status lookups.
- `src/data/schema.js` now treats both automation tables as required.

### Why it matters

Before this work, DataForSEO pulls were not modeled as durable queued work in the gateway. There was no first-class way to say, “enqueue today’s ChatGPT mentions pull for every active site, then drain the queue safely across cron invocations.”

The new tables give the gateway a stable contract for scheduling, execution, retries, and operator visibility.

## 2. Automation Service Was Implemented

A new service was added in `src/services/dataforseo-automation.js`.

### Endpoints queued per site

Each automation batch creates jobs for exactly these four endpoints:

- `aggregated_metrics`
- `top_domains`
- `top_pages`
- `search`

### Core behaviors

- **Feature flag:** automation is opt-in via `DATAFORSEO_AUTOMATION_ENABLED`.
- **Scheduled enqueue:** creates one ChatGPT batch per Manila calendar day (`YYYY-MM-DD`) and inserts jobs for every `active` site.
- **Idempotent schedule key:** duplicate daily enqueues reuse the existing batch instead of creating a second run.
- **Manual enqueue:** creates a one-off batch for a single site ID.
- **Worker claim/lock:** claims pending jobs with `FOR UPDATE ... SKIP LOCKED`, marks them `pulling`, and recovers stale locks.
- **Executor call:** POSTs each claimed job to `${GPTO_DASHBOARD_BASE_URL}/api/internal/dataforseo/execute` with `GPTO_DATAFORSEO_AUTOMATION_TOKEN`.
- **Retry policy:** retryable failures re-queue with delays of 60s, 300s, then 1200s, up to `DATAFORSEO_AUTOMATION_MAX_ATTEMPTS`.
- **Batch rollup:** batch status becomes `queued`, `running`, `succeeded`, `partially_failed`, or `failed` from job counts.
- **Cache invalidation:** when all jobs for a site in a batch succeed, `dashboard_api_cache` entries for `llm_mentions_overview` are deleted for that site.
- **Retry failed jobs:** operators can reset failed jobs in a batch back to `pending`.

### Schedule key detail

`manilaScheduleKey()` uses `Asia/Manila` so the daily batch key flips at Manila midnight, not UTC midnight. Tests cover the UTC boundary around that flip.

## 3. Cron Handlers and Vercel Schedules Were Wired

Two new Vercel cron entrypoints were added:

- `api/internal/cron/dataforseo-enqueue.js`
- `api/internal/cron/dataforseo-worker.js`

Both require `Authorization: Bearer ${CRON_SECRET}` and no-op safely when automation is disabled.

### Cron schedule

`vercel.json` now includes:

| Path | Schedule | Max duration |
|---|---|---:|
| `/internal/cron/dataforseo-enqueue` | `0 16 * * *` (00:00 Manila / 16:00 UTC) | 60s |
| `/internal/cron/dataforseo-worker` | `* * * * *` (every minute) | 300s |

The enqueue cron creates the daily batch. The worker cron drains pending jobs continuously.

## 4. Internal Automation APIs Were Added

`src/routes.js` now exposes:

- `POST /internal/dataforseo/runs` — enqueue a manual one-site batch
- `GET /internal/dataforseo/runs/:batchId` — read batch status and jobs
- `POST /internal/dataforseo/runs/:batchId/retry` — retry failed jobs
- `GET|POST /internal/cron/dataforseo-enqueue` — scheduled enqueue
- `GET|POST /internal/cron/dataforseo-worker` — worker drain

### Auth behavior

Most `/internal` and `/v1` routes still require normal internal auth. The two DataForSEO cron paths accept either `CRON_SECRET` or internal auth via `requireCronOrInternalAuth()`.

## 6. Environment and Configuration Changes

`.env.example` and `README.md` were updated for automation:

- `DATAFORSEO_AUTOMATION_ENABLED` — opt-in flag (`0` by default)
- `GPTO_DATAFORSEO_AUTOMATION_TOKEN` — bearer shared with the GPTO dashboard executor
- `DATAFORSEO_AUTOMATION_CONCURRENCY` — worker concurrency (default 2, capped at 5)
- `DATAFORSEO_AUTOMATION_CLAIM_LIMIT` — jobs claimed per worker run
- `DATAFORSEO_AUTOMATION_MAX_ATTEMPTS` — retry ceiling (default 3)
- `DATAFORSEO_AUTOMATION_LOCK_MINUTES` — stale lock recovery window (default 5)
- `DATAFORSEO_AUTOMATION_REQUEST_TIMEOUT_MS` — executor timeout (default 170000)

`package.json` `type-check` now also syntax-checks the two new cron handlers.
